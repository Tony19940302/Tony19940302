# BattleTracker 项目总体开发方案 V1.0

## 1. 项目定位

项目名称：BattleTracker

项目类型：梦幻西游手游战斗录像分析、计算机视觉识别及战斗资源统计系统。

开发模式：Agent-first Engineering + Harness Engineering。

主要开发Agent：Codex。

### 1.1 项目目标

开发一个能够通过游戏战斗画面识别战斗事件、统计双方人物战斗资源消耗的软件。

核心能力：

1. 识别双方阵法、人物站位和召唤灵站位。
2. 建立人物与召唤灵的固定归属关系。
3. 识别人物使用药品。
4. 识别召唤灵使用药品。
5. 识别人物召唤新召唤灵。
6. 统计每个人物已使用的药品及召唤次数。
7. 在资源上限已知的情况下计算剩余次数。
8. 记录每回合战斗事件。
9. 支持人工纠正错误识别。
10. 支持官方观战数据校准及战斗录像复盘。
11. 后续支持PC及Android应用。
12. 建立可持续训练、评估、调试和改进的视觉识别体系。

### 1.2 项目非目标

当前不开发：

- 游戏自动操作、自动战斗或自动点击。
- 游戏进程内存读取。
- 游戏客户端修改及注入。
- 游戏通信协议拦截。
- 绕过官方观战延迟或安全机制。
- 通用Agent运行平台。
- 与项目无关的大型微服务架构。

第一阶段产品目标为离线录像分析。

只有在确认符合游戏及赛事规则、获得必要许可后，才考虑接入实时战斗屏幕采集和实时资源展示。

所有识别均基于正常可见的游戏画面。

## 3. 游戏业务规则

所有游戏机制必须记录到 `docs/GAME_RULES.md`。

每条规则必须注明：

- 规则编号。
- 规则内容。
- 确认状态。
- 证据来源。
- 是否影响算法设计。
- 对应测试用例。

规则状态分为：

- CONFIRMED：用户明确确认或已有充分证据。
- OBSERVED：在现有录像中观察到，但尚未验证普适性。
- UNKNOWN：未确认。

不得把推测当成已确认规则。

### 3.1 战斗单位

标准5V5战斗包含：

- 己方5个人物。
- 敌方5个人物。
- 每个人物对应一个固定的召唤灵槽位。

逻辑上最多包含20个主要战斗槽位。

人物具有独立身份编号。

例如：

- A1至A5：己方人物。
- B1至B5：敌方人物。
- A_PET_1至A_PET_5：己方宠物槽位。
- B_PET_1至B_PET_5：敌方宠物槽位。

需要区分：

1. 人物身份。
2. 宠物固定槽位。
3. 当前槽位中实际存在的宠物实例。

宠物更换后实例ID变化，但槽位和主人不变。

其他可能出现的召唤物、临时单位和特殊战斗机制应预留扩展能力，不纳入第一版默认统计规则。

### 3.2 人物阵法站位

不同阵法拥有不同的人物1至5号站位。

双方阵营逻辑规则相同，实际画面呈对应镜像布局。

必须通过真实战斗截图校准双方坐标。

不能未经验证直接假设敌方坐标一定等于 `(1-x, y)`。

### 3.3 宠物归属规则

用户已经明确确认：

所有阵法，包括龙飞阵，都采用统一的宠物归属规律。

以阵营自身方向为基准：

| 宠物位置 | 主人 |
|---|---|
| 正中间 | 1号人物 |
| 右侧第一位 | 2号人物 |
| 左侧第一位 | 3号人物 |
| 右侧第二位 | 4号人物 |
| 左侧第二位 | 5号人物 |

从阵营自身左侧到右侧的逻辑排列为：

`[5, 3, 1, 2, 4]`

该排列属于逻辑顺序，不代表直接按照屏幕X坐标排序。

必须根据实际画面方向、阵法和宠物固定槽位进行映射。

宠物死亡、被击飞、离场或更换时：

- 保留其固定槽位。
- 保留主人归属。
- 不重新排列剩余宠物。

### 3.4 药品额度

每个人物拥有独立的用药额度。

人物使用计入额度的药品时：

`该人物 medicine_used + 1`

宠物使用计入额度的药品时：

`该宠物主人 medicine_used + 1`

药品消耗归属于施药者或施药宠物的主人，而不是受药目标。

同一回合，人物及其宠物可能分别用药。

因此同一主人同一回合可能发生多次独立用药事件。

禁止使用主人ID加回合数作为唯一事件去重依据。

目前已知普通战斗画面不会显示具体药品名称。

是否所有药品都存在统一视觉特效，仍待验证。

哪些药品、特殊道具或行为计入额度，必须根据实际官方计数变化验证。

### 3.5 召唤额度

每个人物拥有独立的召唤次数。

人物成功召唤新宠物时：

`pet_used + 1`

宠物死亡不增加召唤次数。

普通宠物复活不能直接视为新召唤。

现有录像中，开局第一只出场宠物已经计入召唤次数。

因此在适用的战斗模式下，开局宠物已使用次数为1。

该初始化规则必须与具体战斗模式及初始官方快照对应，不适用于所有未知场景。

用户已确认，普通战斗中召唤宠物时存在召唤文字提示。

### 3.6 官方观战计数器

官方观战开启详细信息后，在人物附近显示药品及召唤次数。

现有录像观察到：

- 药品：0/10、1/10等。
- 召唤：1/6、2/6、1/7等。

数据格式为：

`已使用次数 / 总次数上限`

不是剩余次数。

软件应独立记录：

- medicine_used
- medicine_limit
- pet_used
- pet_limit

计算公式：

`medicine_remaining = medicine_limit - medicine_used`

`pet_remaining = pet_limit - pet_used`

### 3.7 动态资源上限

现有录像已经观察到召唤次数分母从6变化为7。

说明资源上限可能在战斗过程中改变。

禁止在业务核心中将所有资源上限全局硬编码为10和6。

需要支持：

- 初始上限配置。
- 动态上限变化。
- 上限未知。
- 上限来源记录。
- 官方快照校准。
- 人工修正。
- 不确定状态提示。

额外资源上限增加的触发机制、视觉提示及可识别性仍需验证。

如果上限无法通过普通画面获知，不允许伪造准确的剩余次数。

应显示已确认消耗、已知上限或明确的未知状态。

如果录像从战斗中途开始，且没有可靠初始快照，也不能假定之前的用药次数为0。

### 3.8 观战延迟

用户确认官方观战存在约两回合延迟。

可以在录像分析或得到许可的场景中，利用官方观战状态作为校准参考。

不能直接按墙上时钟进行固定两回合偏移。

需要根据比赛身份、回合、行动序列及计数快照的实际对应关系进行校准。

官方延迟数据只代表对应历史时刻的状态，不能冒充当前实时状态。

### 3.9 当前未确认的机制

必须持续研究：

1. 所有药品是否具有统一受药特效。
2. 不同宠物用药动作是否具有共同特征。
3. 普通治疗技能与用药是否可以稳定区分。
4. 资源上限增加时是否存在可见提示。
5. 特殊召唤行为是否消耗召唤次数。
6. 实战视角与普通观战视角是否存在影响识别的差异。
7. 第三行官方观战数字的实际含义。

未经确认的规则不得进入强制业务逻辑。

## 4. 总体技术架构

系统分为三个主要子系统。

### 4.1 战斗识别与统计系统

流程：

视频输入 → 画面预处理 → 阵法识别 → 战斗槽位定位 → 行动候选检测 → 事件分类 → 主人映射 → 战斗状态更新 → UI展示及事件保存。

核心模块：

- VideoSource
- FrameProcessor
- FormationEngine
- SlotTracker
- ActorDetector
- EventDetector
- BattleStateEngine
- EventStore
- UserInterface

### 4.2 数据与模型系统

流程：

官方详细录像 → 计数器提取 → 参考事件生成 → 双录像对齐 → 训练样本生成 → 标签复核 → 数据集划分 → 模型训练 → 模型评估 → 错误样本回流。

核心模块：

- CounterExtractor
- VideoAligner
- AnnotationManager
- DatasetBuilder
- ModelTrainer
- ModelEvaluator
- FailureCaseManager

### 4.3 Harness Engineering 系统

负责：

- 项目知识管理。
- 开发阶段管理。
- Agent执行规范。
- 自动化测试。
- 数据完整性检查。
- 模型评估。
- 架构约束。
- 失败案例调试。
- 代码审查。
- 版本及实验追踪。

Harness属于项目工程体系，不是独立的通用Agent平台。

初始推荐技术栈：

Python依赖应锁定可用版本。

禁止一次安装所有未来可能使用的重型依赖。

阶段0和1只安装必要依赖。

后续根据实际需求逐步加入OCR、PyTorch及桌面GUI依赖。

## 7. 核心数据模型

### 7.1 Formation

负责描述阵法。

字段包括：

- formation_id
- formation_name
- player_slots
- pet_slots
- pet_owner_mapping
- coordinate_system
- calibration_version

人物和宠物槽位应支持归一化坐标、检测区域及视角变换。

未知坐标允许为空。

不得编造真实战斗坐标。

### 7.2 PlayerState

```python
@dataclass
class PlayerState:
    player_id: str
    formation_slot: int
    medicine_used: int | None = None
    medicine_limit: int | None = None
    pet_used: int | None = None
    pet_limit: int | None = None
    current_pet_id: str | None = None
    alive: bool | None = None
```

需要增加状态来源、确认状态及最近更新时间等必要信息。

剩余次数仅在已使用次数与上限均可靠时计算。

如果信息缺失，保留未知状态。

不要通过强行截断数值掩盖错误计数。

### 7.3 PetSlot与PetState

PetSlot表示固定归属：

- slot_id
- owner_id
- formation_slot
- screen_position

PetState表示实际宠物实例：

- pet_instance_id
- pet_name
- owner_id
- slot_id
- alive
- summon_round
- departure_round

### 7.4 BattleState

负责整场战斗状态：

- battle_id
- battle_mode
- current_round
- ally_formation
- enemy_formation
- players
- pet_slots
- current_timestamp
- event_history
- uncertainty_flags

### 7.5 BattleEvent

统一事件结构示例：

```json
{
  "event_id": "battle001_event023",
  "battle_id": "battle001",
  "round": 2,
  "timestamp_ms": 29500,
  "actor_id": "A_PET_2",
  "owner_id": "A2",
  "target_id": "A1",
  "event_type": "USE_MEDICINE",
  "confidence": 0.96,
  "source": "vision",
  "status": "candidate"
}
```

该JSON仅为结构示例，不表示现有录像中的事件已经全部准确确认。

事件必须支持：

- 原始视频时间戳。
- 行动开始和结束时间。
- 行动者。
- 资源归属人物。
- 受作用目标。
- 事件类型。
- 事件来源。
- 置信度。
- 确认状态。
- 证据截图或片段。
- 模型或算法版本。
- 事件修订记录。

### 7.6 EventType

至少支持：

- BATTLE_START
- ROUND_START
- USE_MEDICINE
- SUMMON_PET
- PET_DEPARTURE
- PET_REVIVAL
- PLAYER_DEATH
- PLAYER_REVIVAL
- MEDICINE_LIMIT_CHANGE
- PET_LIMIT_CHANGE
- OFFICIAL_SNAPSHOT
- MANUAL_CORRECTION
- EVENT_RETRACTED
- UNKNOWN_ACTION
- BATTLE_END

状态引擎应采用可回放的事件记录机制。

允许撤销、修正及重新计算，而不是只保存当前计数。

候选事件与已确认事件分开管理。

同一动作重复识别时不能重复计数。

来自官方计数、视觉预测和人工标注的同一个事件必须能够关联，不能重复消耗。

## 8. Harness Engineering完整要求

### 8.1 AGENTS.md

AGENTS.md应作为简短项目导航，而不是复制整个项目需求。

包括：

- 项目目标。
- 当前开发阶段。
- 关键约束。
- 重要文档位置。
- 测试及验证入口。
- 修改代码的基本要求。
- 完成任务的判断标准。

要求Agent开发前先阅读相关文档。

禁止仅根据聊天历史猜测项目状态。

### 8.2 项目知识库

维护以下文件：

- GAME_RULES.md：业务规则、证据、确认状态。
- ARCHITECTURE.md：模块职责及接口。
- DECISIONS.md：架构决策及原因。
- PROJECT_PROGRESS.md：当前进度及实际完成状态。
- KNOWN_ISSUES.md：缺陷及待解决事项。
- RESEARCH_NOTES.md：视觉特征、实验发现。
- TEST_PLAN.md：测试方法及验收标准。

当新录像推翻旧假设时，必须及时更新规则及实验记录。

### 8.3 阶段执行计划

在 `harness/plans/` 下管理Phase 0至Phase 8。

每个阶段计划应包含：

1. Objective。
2. Scope。
3. Non-goals。
4. Dependencies。
5. Tasks。
6. Acceptance Criteria。
7. Verification Commands。
8. Known Risks。
9. Completion Evidence。

阶段结束必须保存真实验收结果。

不能仅因代码文件存在，就标记功能已完成。

### 8.4 统一自动验证入口

创建：

```bash
python tools/verify.py --profile phase-01
```

后续扩展：

```bash
python tools/verify.py --profile phase-02
python tools/verify.py --profile phase-04
python tools/verify.py --profile full
```

验证内容逐步包括：

- 单元测试。
- 集成测试。
- 回归测试。
- 配置校验。
- 数据集完整性。
- 数据泄漏检测。
- 模型指标评估。
- 架构依赖检查。
- 必要的性能测试。

输出结构化JSON报告。

至少包含：

- profile
- check_name
- command
- status
- exit_code
- duration
- result_summary
- artifact_paths
- failure_reason

状态使用：

- PASS
- FAIL
- SKIPPED

SKIPPED不能冒充PASS。

必要验证失败时，统一验证程序应返回非零退出码。

禁止通过删除测试、降低验收要求、修改真实标签或隐藏异常来使验证通过。

### 8.5 Evaluation Harness

视觉项目必须独立于普通软件测试建立评估体系。

评估输入：

1. 官方详细观战数据。
2. 人工复核参考事件。
3. 不带详细信息的录像。
4. 程序预测事件。
5. 双录像对齐关系。

评估内容：

- 事件是否真实发生。
- 事件类型是否正确。
- 行动者是否正确。
- 主人归属是否正确。
- 时间及回合是否匹配。
- 资源计数是否一致。
- 资源上限是否一致。
- 未知和低置信度比例。

预测事件与参考事件应进行一对一匹配。

同一个真实事件不能被多个预测事件重复计为正确。

事件时间容差必须明确配置，并根据实际录像对齐误差验证。

每次评估应生成：

- metrics.json
- evaluation_report.md
- false_positives.jsonl
- false_negatives.jsonl
- ownership_errors.jsonl
- 失败案例截图或片段索引

### 8.6 Debug Harness

后续逐步建立：

```bash
python tools/inspect_video.py --help
python tools/inspect_event.py --help
python tools/extract_counters.py --help
python tools/evaluate.py --help
```

使Codex能够直接获取：

- 指定时间点的原始画面。
- 某个事件前后的连续帧。
- 人物及宠物槽位检测框。
- OCR识别区域和原始结果。
- 模型分类结果。
- 官方计数变化。
- 误识别的具体原因。

可复现的调试工具优先于大量文字日志。

### 8.7 Skills

初期只建立必要Skills：

`phase-development`

负责：

- 阅读项目规则。
- 确认任务范围。
- 执行阶段计划。
- 实现代码。
- 运行验证。
- 更新进度及证据。

`code-review`

负责：

- 检查业务规则。
- 检查模块依赖。
- 检查测试覆盖。
- 查找边界错误。
- 检查未验证假设。

`vision-evaluation`

在视觉评估工具实际实现后建立。

负责：

- 运行指定数据集评估。
- 分析误识别及漏识别。
- 生成失败案例。
- 比较不同算法版本。
- 判断是否出现识别退化。

不得创建大量没有实际执行能力的空壳Skills。

### 8.8 Agent开发闭环

每次开发任务遵循：

需求 → 读取上下文 → 制定计划 → 实现 → 验证 → 分析失败 → 修正 → 独立审查 → 再次验证 → 更新文档。

必须限制无效重复修复。

如果同一问题持续失败，应记录尝试过的方法、证据、当前阻塞和下一步建议。

不得无限循环修改。

## 9. 多Agent协作方案

### 9.1 基本原则

优先使用Codex已有的Agent及子Agent能力。

不自行开发通用多Agent调度框架。

多Agent属于按需使用的工程手段，而不是每个阶段的强制要求。

当前环境不支持子Agent时，允许单Agent顺序完成同样的工作。

### 9.2 Agent角色

Coordinator：

- 阅读总体方案。
- 制定阶段计划。
- 设计模块接口。
- 分配任务。
- 管理依赖。
- 集成代码。
- 最终验收。

Developer：

- 实现指定模块。
- 编写必要测试。
- 遵守已定义接口。

QA：

- 独立设计测试。
- 检查边界条件。
- 验证业务规则。
- 防止测试只覆盖实现者假设。

Reviewer：

- 独立代码审查。
- 检查架构问题。
- 检查数据泄漏。
- 检查验证证据。
- 默认只读审查，不直接改动其他Agent代码。

Vision Researcher：

- 分析战斗录像。
- 研究动作及特效。
- 比较识别算法。
- 建立实验记录。
- 输出失败案例。

### 9.3 各阶段Agent使用策略

Phase 0：

单主Agent即可。

Phase 1：

主Agent开发，独立QA或Reviewer按需检查。

Phase 2：

可以并行研究计数器定位、OCR算法和人工参考标签。

Phase 3：

可以并行进行视频对齐、标签质量检查及数据集验证。

Phase 4：

可以并行研究召唤识别、行动者识别及用药规则。

Phase 5：

重点使用多Agent进行不同模型方案实验。

Phase 6：

使用独立评估Agent与Reviewer检查完整比赛效果。

Phase 7和8：

核心接口稳定后，可以并行处理PC及Android产品化任务。

### 9.4 并行开发约束

- 先定义模块接口，再并行实现。
- 不允许多个Agent无协调地修改同一文件。
- 需要并发写代码时，使用独立分支或Git worktree。
- 每个Agent必须有明确任务及验收标准。
- 所有Agent使用统一的游戏规则和评估定义。
- 主Agent负责合并及完整验证。
- 算法实验采用一致的数据、指标和计算预算。
- 不因Agent数量增加而降低测试质量。

## 12. Phase 2：官方详细观战录像解析器

### 12.1 目标

从带详细信息的录像自动提取10个人物的官方资源计数。

### 12.2 识别方案

根据真实战斗截图建立人物计数器ROI。

分别截取：

- 药品计数区域。
- 召唤计数区域。
- 当前回合区域。
- 阵法图标区域。

优先尝试：

1. 固定数字模板匹配。
2. 图像颜色及区域分割。
3. OCR。
4. 多帧稳定性判断。

不要一开始对整张高分辨率战斗画面频繁运行OCR。

### 12.3 计数稳定性

需要处理：

- 战斗特效遮挡。
- OCR误读。
- 数字短暂消失。
- 角色运动。
- 不同分辨率。
- 视频跳帧。
- 新回合及计数更新时机。

保留原始OCR结果及过滤结果。

计数跳变应记录为可疑事件。

不能因为连续两次有效读数相差2，就未经验证拆成两个精确时间的用药事件。

### 12.4 输出

生成：

- official_snapshots.jsonl
- official_events.jsonl
- counter_extraction_report.json
- 无法识别或可疑计数的截图。

官方事件至少区分：

- USE_MEDICINE
- SUMMON_PET
- MEDICINE_LIMIT_CHANGE
- PET_LIMIT_CHANGE

官方计数变化可能只能确定主人，不能直接确定是人物还是宠物实际行动。

必须保留这一不确定性。

### 12.5 验收标准

对现有详细录像建立人工复核参考数据。

自动提取结果与人工参考数据进行逐项比较。

报告识别正确率、未知比例及具体错误位置。

暂时不要求支持所有阵法、所有战斗背景。

## 13. Phase 3：双录像对齐与数据集建设

### 13.1 目标

利用官方详细录像产生参考标签，再将标签转移到关闭详细信息的对应录像。

### 13.2 视频对齐

不能简单使用固定秒数偏移。

需要结合：

- 比赛身份。
- 回合数。
- 技能顺序。
- 行动者。
- 伤害或治疗数字。
- 特殊战斗事件。

第一版允许人工指定时间锚点。

后续再尝试自动序列匹配或分段时间映射。

### 13.3 样本生成

每个训练样本记录：

- battle_id
- source_video_id
- round
- clip_start
- clip_end
- event_type
- actor_id
- owner_id
- target_id
- official_counter_before
- official_counter_after
- alignment_confidence
- annotation_status

用药标签可由官方计数变化自动生成候选。

实际施药者需要额外通过视频复核确认。

训练数据必须优先使用无官方计数器的画面。

使用详细录像作为输入时，必须去除计数器及其他可能泄漏答案的区域。

### 13.4 数据类别

正样本：

- 人物用药。
- 宠物用药。
- 人物召唤。

困难负样本：

- 化生寺治疗。
- 普陀山治疗。
- 宠物治疗技能。
- 神佑复活。
- 特技。
- 法宝。
- 被动回血。
- 普通施法动作。
- 普通攻击。
- 宠物离场及重新出现。
- 待机动画。

特殊样本：

- 药品上限变化。
- 召唤上限变化。
- 遮挡。
- 多个动作连续发生。
- 无法确定行动者。

### 13.5 数据集划分

必须按完整比赛分组。

同一场比赛的：

- 详细录像。
- 无详细录像。
- 不同截取片段。
- 不同背景或重复播放版本。

必须属于同一数据集分组。

禁止随机按帧划分训练集和测试集。

建议数据集分为：

- Train：训练。
- Validation/Dev：算法选择及参数调整。
- Golden Test：锁定的最终独立测试。

现有一场比赛只适合用于开发验证，不能据此宣称模型具备样本外泛化能力。

最终测试集不得用于训练或反复参数调优。

### 13.6 数据规模

建议逐步积累：

- 1至3场：流程验证。
- 10至20场：传统识别基线。
- 30至50场：初步模型训练。
- 更多比赛：扩大阵法、门派、宠物及背景覆盖。

实际是否足够，以有效事件数量、类别分布和泛化表现判断，不以比赛场次数量作为唯一标准。

### 13.7 验收标准

- 至少完成现有两份录像的可靠对齐。
- 建立可追溯的用药及召唤事件样本。
- 标签可以人工检查及修改。
- 所有样本能回溯原始录像。
- 自动检查数据泄漏。
- 不将未经复核的候选标签当作最终真实答案。

## 14. Phase 4：传统视觉识别基线

### 14.1 总原则

优先使用可解释、低成本的视觉算法。

先测量传统方法的真实效果，再决定是否引入深度学习。

### 14.2 阵法识别

利用：

- 开局阵法图标。
- 人物位置。
- 宠物固定槽位。
- 画面方向。
- 实际战斗区域。

使用模板匹配及预设阵法配置。

第一版允许人工选择阵法及校准站位。

后续自动识别。

### 14.3 行动者识别

对双方20个主要战斗槽位进行局部分析。

候选特征：

- 帧间差分。
- 局部光流。
- 动作开始时间。
- 人物武器动作。
- 宠物姿态变化。
- 局部特效变化。
- 动作方向。
- 目标状态变化。

不能简单根据哪个区域运动最强来判断行动者。

必须考虑受击者、背景动画及跨区域特效。

### 14.4 召唤识别

联合以下信号：

1. 召唤文字。
2. 召唤者位置。
3. 召唤光效。
4. 对应宠物槽位变化。
5. 新宠物模型或血条出现。

召唤文字可能使用固定模板匹配或OCR。

使用多信号融合，不强制要求所有信号同时出现。

需要检测事件开始和结束。

避免同一召唤持续显示多帧而重复计数。

### 14.5 用药识别

重点研究：

- 人物用药动作。
- 宠物用药动作。
- 施药者与目标的时序关系。
- 目标回血。
- 目标回蓝。
- 目标复活。
- 目标解除封印。
- 是否出现门派技能、特技或法宝名称。

当前录像发现不同人物与宠物动作可能存在差异。

尚不能确认黄色光效为用药专属特效。

因此不能仅根据光效颜色或绿色治疗数字判定用药。

没有检测到技能文字，也不能直接认定为用药。

第一版应允许输出：

- MEDICINE_CANDIDATE
- MEDICINE_CONFIRMED
- NON_MEDICINE
- UNKNOWN

根据实际评估结果逐步调整置信度阈值。

### 14.6 事件状态机

建议事件生命周期：

IDLE → ACTION_CANDIDATE → ACTION_CLASSIFIED → EVENT_CONFIRMED或UNKNOWN → ACTION_END。

需要支持：

- 短暂遮挡。
- 同一个动作多次检测。
- 不同行动快速连续发生。
- 多个候选行动者。
- 人物与宠物归属。
- 置信度不足时暂缓确认。

离线识别可以利用动作之后的画面完成判定。

未来实时模式只能使用当前及已经发生的画面，不得利用尚未发生的后续帧伪造低延迟结果。

### 14.7 验收标准

在不读取官方计数器的情况下，输出完整预测事件。

使用Phase 3参考数据测量真实识别指标。

记录所有失败案例。

## 15. Phase 5：AI模型增强与多Agent实验

### 15.1 启动条件

只有传统视觉识别无法满足要求时，才正式启动模型训练。

必须先建立：

- 有效训练数据。
- 可靠验证集。
- 可执行评估工具。
- 传统识别基线。
- 明确失败案例。

### 15.2 候选方案

方案A：

OpenCV特征＋规则分类。

方案B：

轻量CNN图像特征＋时序分类。

方案C：

MobileNetV3＋TCN。

方案D：

其他经过实验验证的轻量视频动作识别模型。

不能预先认定YOLO、TCN或Transformer一定是最优方案。

### 15.3 模型输入

可以包含：

- 行动者局部连续帧。
- 宠物局部连续帧。
- 目标区域。
- 全局战斗画面。
- OCR技能信息。
- 光流或运动特征。
- 血条及状态变化。
- 槽位归属信息。

重点研究多帧时序关系，而不是只对单帧进行分类。

### 15.4 模型输出

至少支持：

- 行动者类型。
- 行动者槽位。
- 用药。
- 召唤。
- 非用药动作。
- 未知动作。
- 分类置信度。

必要时拆成多个轻量模型，不强制一个模型负责全部任务。

### 15.5 多Agent实验

主Agent制定统一实验协议。

Agent A研究传统特征方案。

Agent B研究轻量CNN及时序方案。

Agent C研究其他可部署的动作识别方案。

统一使用：

- 相同训练数据版本。
- 相同验证集。
- 相同评价指标。
- 可比较的训练预算。
- 固定随机种子或可记录随机状态。

记录：

- 实验ID。
- 模型结构。
- 训练配置。
- 数据集版本。
- 代码版本。
- 训练指标。
- 验证指标。
- 推理耗时。
- 内存消耗。
- 失败案例。

主Agent基于实际验证结果选择方案。

### 15.6 模型部署

- 置信度阈值。

## 16. Phase 6：完整比赛评估与回归测试

### 16.1 评估指标

必须评估：

- 人物用药Precision。
- 人物用药Recall。
- 宠物用药Precision。
- 宠物用药Recall。
- 召唤Precision。
- 召唤Recall。
- 行动者识别准确率。
- 主人归属准确率。
- 未知事件比例。
- 每回合资源计数一致率。
- 每场比赛最终资源一致率。
- 累计计数绝对误差。
- 最大累计偏差。
- 识别延迟。
- 推理性能。

Precision表示预测为该事件的结果中有多少是真的。

Recall表示真实事件中有多少被成功识别。

不能仅使用总体分类准确率。

### 16.2 初始工程目标

建议目标：

- 用药Precision和Recall均达到98%以上。
- 召唤Precision和Recall均达到99%以上。
- 主人归属准确率达到99%以上。
- 回合末资源一致率达到95%以上。

这些是研发目标，不是当前已实现结果。

具体发布标准应根据独立比赛实测进一步确定。

必须单独报告每场比赛是否存在累计误差。

即使单事件准确率很高，如果长时间比赛产生严重累计误差，也不能视为满足最终需求。

### 16.3 评估维度

按照以下维度分组统计：

- 人物与宠物。
- 不同阵法。
- 不同门派。
- 不同宠物模型。
- 不同背景。
- 不同分辨率。
- 不同播放速度。
- 遮挡情况。
- 不同药品效果。
- 普通观战与实际参战视角。

数据不足的维度应标记为未验证。

### 16.4 回归体系

将典型失败案例保存为固定回归测试。

后续每次修改识别算法，都必须验证以前已经正确识别的场景没有明显退化。

禁止使用最终测试集进行反复调参。

### 16.5 验收标准

- 在独立比赛上完成完整端到端评估。
- 输出正式识别报告。
- 误识别事件可以定位到视频证据。
- 明确模型尚未解决的场景。
- 未达标时返回Phase 3、4或5继续改进。

## 19. 持续优化机制

建立以下闭环：

收集新录像 → 提取官方计数 → 对齐无详细录像 → 生成候选标签 → 人工复核 → 训练或优化规则 → 验证集评估 → 分析失败案例 → 重新改进 → 独立测试 → 发布新版本。

所有模型及算法必须能够追踪：

- 对应代码版本。
- 对应数据版本。
- 配置参数。
- 评估报告。
- 已知限制。

新增训练数据不能污染锁定测试集。

新版本如果在关键识别场景出现明显退化，不能仅因为平均准确率提升就直接替换旧版本。
